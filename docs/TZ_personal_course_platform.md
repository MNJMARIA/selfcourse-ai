**Назва проєкту:** SelfCourse AI

**Автор ТЗ:** Марія Степанова
**Дата:** вересень 2026

## Частина 1. Технічне завдання

### 1. Загальна інформація

#### 1.1 Призначення документа
Цей документ визначає функціональні та нефункціональні вимоги до системи, її архітектуру, модель даних та критерії приймання. Слугує основою для самостійної розробки продукту.

#### 1.2 Мета проєкту
Створити персональний інструмент, що перетворює довільні навчальні матеріали (документи курсів, конспекти, підручники) на структурований інтерактивний курс у стилі Coursera: з розбиттям на розділи/підкурси, текстовим викладом матеріалу, автоматично згенерованими тестами, відстеженням прогресу та архівацією завершених курсів.

#### 1.3 Терміни та скорочення
| Термін | Опис |
|---|---|
| Курс | Набір навчального матеріалу, згенерований з одного або кількох завантажених файлів |
| Підкурс / модуль | Логічна частина курсу (розділ), на які розбивається великий обсяг матеріалу |
| Урок | Мінімальна текстова одиниця контенту в межах модуля |
| Тест | Набір автоматично згенерованих запитань до уроку/модуля |
| Прогрес | % пройденого контенту + середній результат тестів |
| LLM | Мовна модель, яка використовується для генерації тексту курсу і тестів |

#### 1.4 Цільовий користувач
Один користувач (single-tenant, особистий застосунок), з можливістю розширення до кількох акаунтів у майбутньому. Основний сценарій — самонавчання на основі платних/приватних курсів, конспектів, PDF-книг тощо.

### 2. Опис предметної області

#### 2.1 Проблема
Матеріали навчання (docx, pdf, pptx, txt) часто розкидані, немає структурованого способу пройти їх послідовно, перевірити засвоєння і відстежити прогрес — на відміну від платформ типу Coursera, які так не дозволяють використовувати *власний* матеріал.

#### 2.2 Ключова вимога — конфіденційність
Частина матеріалів — це персонально оплачені курси третіх сторін. Ці дані:
- **не повинні потрапляти у публічний простір**;
- **не повинні використовуватись для тренування сторонніх моделей**;
- бажано, щоб взагалі **не залишали пристрій користувача** без потреби.

Ця вимога є наскрізною і впливає на вибір архітектури й стека (див. розділ 4.1 та 7).

#### 2.3 Основний сценарій використання (User flow)
1. Користувач реєструється/входить в акаунт.
2. Завантажує один або декілька файлів (docx/doc/pptx/pdf/txt).
3. Система аналізує обсяг і структуру матеріалу.
4. Якщо матеріалу багато — розбиває курс на підкурси/модулі.
5. Генерує текстовий виклад (уроки) + тести до кожного модуля.
6. Курс з'являється в акаунті зі статусом "не розпочато".
7. Користувач проходить уроки → статус "активний", прогрес оновлюється в %.
8. Після кожного модуля — тест, результат зберігається.
9. Після проходження 100% і завершення всіх тестів курс автоматично переходить у статус "архівний".
10. У акаунті є 3 розділи: **Активні / Не розпочаті / Архівні** курси.

### 3. Функціональні вимоги

#### 3.1 Керування акаунтом
- FR-1.1: Реєстрація/вхід (email + пароль, хешування пароля).
- FR-1.2: Особистий кабінет з трьома вкладками курсів (активні, не розпочаті, архів).
- FR-1.3: Видалення курсу/матеріалів користувачем повністю (right to delete).

#### 3.2 Завантаження матеріалів
- FR-2.1: Підтримка форматів: `.docx`, `.doc`, `.pptx`, `.pdf`, `.txt`.
- FR-2.2: Можливість завантажити кілька файлів як один курс.
- FR-2.3: Валідація формату та розміру файлу, повідомлення про помилку.
- FR-2.4: Індикатор прогресу обробки (парсинг → генерація).

#### 3.3 Генерація курсу
- FR-3.1: Автоматичне вилучення тексту з файлів (з урахуванням структури — заголовки, слайди, абзаци).
- FR-3.2: Якщо обсяг тексту перевищує заданий поріг — автоматичний поділ на підкурси/модулі за смисловими блоками.
- FR-3.3: Генерація зв'язного текстового викладу (уроків) на основі вихідного матеріалу (без вигадування фактів, яких немає в матеріалі).
- FR-3.4: Генерація тестових запитань (одиночний вибір, множинний вибір, коротка відповідь) до кожного модуля на основі його вмісту.
- FR-3.5: Можливість регенерувати тест/урок, якщо якість незадовільна.

#### 3.4 Проходження курсу
- FR-4.1: Послідовне або довільне проходження уроків усередині модуля.
- FR-4.2: Позначення уроку як пройденого.
- FR-4.3: Проходження тесту після модуля з підрахунком результату.

#### 3.5 Прогрес та оцінювання
- FR-5.1: Розрахунок % пройденого матеріалу = (пройдені уроки / загальна кількість уроків).
- FR-5.2: Розрахунок середньої оцінки за тестами курсу.
- FR-5.3: Відображення прогрес-бару на рівні курсу і модуля.

#### 3.6 Архівація
- FR-6.1: При досягненні 100% проходження + проходження всіх тестів курс автоматично переводиться у статус "архівний".
- FR-6.2: Архівний курс доступний тільки для перегляду (read-only) з фінальною оцінкою.
- FR-6.3: Можливість вручну "розархівувати" курс для повторного проходження.

### 4. Нефункціональні вимоги

#### 4.1 Безпека та конфіденційність (критична вимога)
- NFR-1.1: Дані користувача та вміст курсів не повинні передаватись у публічні або треті сервіси без явної згоди користувача.
- NFR-1.2: Якщо для генерації використовується зовнішній AI API — обов'язково обирати провайдера з політикою "без збереження і тренування на даних", або, за можливості, використовувати локальну (self-hosted) модель.
- NFR-1.3: Шифрування файлів і тексту курсів at rest (наприклад AES-256).
- NFR-1.4: Паролі — лише у хешованому вигляді (bcrypt/argon2).
- NFR-1.5: З'єднання клієнт-сервер лише через HTTPS/захищений тунель, навіть у межах домашньої мережі.
- NFR-1.6: Логи застосунку не повинні містити повний текст завантажених матеріалів.

#### 4.2 Кросплатформність
- NFR-2.1: Доступ з ПК (браузер) і смартфона без встановлення нативного застосунку — **responsive web app / PWA**.
- NFR-2.2: Коректне відображення на екранах від ~360px (мобільні) до desktop.

#### 4.3 Вартість
- NFR-3.1: Усі використані сервіси, бібліотеки, хостинг — на безкоштовних тарифах або self-hosted рішеннях без ліцензійних витрат.
- NFR-3.2: Архітектура має враховувати ліміти безкоштовних тарифів (обсяг сховища, квоти запитів до AI).

#### 4.4 Продуктивність
- NFR-4.1: Генерація курсу з файлу середнього обсягу (~30–50 стор.) — прийнятний час очікування (орієнтовно до кількох хвилин, з індикацією прогресу, а не "заморожуванням" інтерфейсу).

#### 4.5 Юзабіліті
- NFR-5.1: Інтерфейс інтуїтивний, без потреби в інструкції — максимум 3 кліки від завантаження файлу до початку курсу.

### 5. Модель даних (основні сутності)

```
User
 ├─ id, email, password_hash, created_at

Course
 ├─ id, user_id, title, status [not_started | active | archived]
 ├─ source_files[], created_at, archived_at

Module (Підкурс)
 ├─ id, course_id, title, order_index

Lesson (Урок)
 ├─ id, module_id, title, content_text, order_index, is_completed

Quiz
 ├─ id, module_id, questions[]

Question
 ├─ id, quiz_id, type [single|multi|short], text, options[], correct_answer

QuizAttempt
 ├─ id, quiz_id, user_id, score, answers[], completed_at

ProgressRecord
 ├─ course_id, percent_completed, average_score, updated_at
```

### 6. Архітектура системи (високий рівень)

```
[ Клієнт: Web / PWA (ПК + телефон) ]
              │  HTTPS / захищений тунель
              ▼
[ Backend API (auth, курси, прогрес) ]
              │
     ┌────────┼─────────────┐
     ▼        ▼              ▼
[Парсер     [Модуль AI-    [База даних
 файлів]     генерації      (зашифрована)]
             курсу/тестів]
     │        │
     ▼        ▼
[docx/pdf/  [Локальна LLM
 pptx/txt   (Ollama) АБО
 → текст]   API з політикою
            no-retention]
```

Ключове архітектурне рішення: **AI-модуль ізольований від зовнішнього світу за замовчуванням** (локальна модель), щоб приватні матеріали не покидали пристрій користувача. Хмарний AI API — лише як опційний fallback.

### 7. Технологічний стек

Підібраний з урахуванням наявних навичок з резюме (Python, Flask, Java, SQL, REST API, Prompt Engineering, Generative AI) + кар'єрно логічні доповнення (сучасні, затребувані на ринку технології).

| Компонент | Технологія | Коментар |
|---|---|---|
| Backend API | **Python + FastAPI** | Логічне продовження знань Flask, зараз більш затребуваний на ринку; безкоштовний |
| Парсинг файлів | `python-docx`, `python-pptx`, `pdfplumber`/`PyMuPDF` | Безкоштовні бібліотеки для вилучення тексту |
| AI-генерація контенту й тестів | **Ollama + локальна модель** (Llama 3.1 8B / Mistral 7B) як основний варіант; хмарне API — лише опційно | Забезпечує приватність і нульову вартість |
| База даних | **SQLite** (для персонального використання) або **PostgreSQL** (Supabase/Neon free tier) | SQLite — найпростіше й безкоштовне рішення для одного користувача |
| Аутентифікація | JWT + bcrypt | Стандарт, безкоштовний |
| Frontend | **React + Tailwind CSS**, зібраний як **PWA** | Кар'єрно затребувана навичка, одна кодова база під ПК і телефон |
| Доступ з телефону | **Tailscale (free tier)** або self-hosted VPN-тунель до домашнього сервера | Дозволяє не виставляти дані у публічний інтернет |
| Контроль версій / CI | GitHub (вже є акаунт), GitHub Actions (free tier) | Вже використовується (GitHub у резюме) |
| Контейнеризація (опційно) | Docker | Спрощує розгортання, кар'єрно корисний скіл |

**Про хостинг — два варіанти (обрати залежно від пріоритету):**

1. **Local-first (максимальна приватність, 100% безкоштовно):** backend + AI працюють на власному ПК/домашньому сервері, доступ з телефону — через Tailscale/VPN. Дані фізично не покидають пристрій.
2. **Хмарний free-tier (зручніше, доступ будь-звідки):** Render/Fly.io free tier для backend, Vercel/Netlify для frontend, Supabase для БД. Потребує додаткового шифрування даних на сервері третьої сторони і уважного вибору AI-провайдера (no-retention policy), оскільки дані технічно покидають пристрій.

### 8. Обмеження та припущення
- Проєкт розробляється однією людиною за допомогою AI-асистентів (не команда).
- Пріоритет — 100% безкоштовність над зручністю масштабування.
- Один користувач (multi-tenant — можлива майбутня ітерація, не MVP).
- Якість автогенерованих тестів залежить від якості вихідного матеріалу і обраної моделі.

### 9. Критерії приймання (Definition of Done для MVP)
- [ ] Користувач може зареєструватись і увійти в акаунт.
- [ ] Можна завантажити файл одного з підтримуваних форматів.
- [ ] Система генерує курс з текстовими уроками і хоча б одним тестом на модуль.
- [ ] Прогрес (%) і оцінка за тестами коректно відображаються та оновлюються.
- [ ] Курс автоматично архівується при 100% проходженні.
- [ ] Акаунт коректно показує 3 категорії курсів.
- [ ] Дані матеріалів не передаються нікуди, крім локального AI-модуля / обраного no-retention API.
- [ ] Інтерфейс коректно працює як на ПК, так і на смартфоні (перевірено вручну на реальних пристроях).

### 10. Ризики
| Ризик | Вплив | Мітигація |
|---|---|---|
| Локальна LLM повільна/слабка на слабкому "залізі" | Довга генерація, нижча якість тестів | Можливість fallback на хмарне API з no-retention політикою |
| Втрата форматування при парсингу складних pptx/pdf | Гірша якість уроків | Ручна перевірка + можливість регенерації |
| Тести з галюцинаціями (AI вигадує факти) | Недостовірні тести | Промпт з жорсткою вимогою "лише на основі наданого тексту", ручна валідація перед фінальним використанням |
| Вихід за ліміти безкоштовних тарифів | Простій сервісу | Local-first підхід як основний, моніторинг квот |

## Частина 2. Послідовний план розробки

### Етап 0. Підготовка (1 фаза, ~тиждень)
1. Зафіксувати MVP-скоуп (мінімальний набір функцій з розділу 3, без "зайвих" фіч).
2. Обрати основний варіант архітектури: local-first чи хмарний free-tier (розділ 7).
3. Створити репозиторій на GitHub, налаштувати структуру проєкту (backend/frontend/docs).
4. Встановити середовище розробки: Python 3.11+, Node.js, Docker (опційно).

### Етап 1. Backend MVP: авторизація і базова структура
1. Розгорнути FastAPI-проєкт (спираючись на наявний досвід Flask — синтаксис дуже схожий).
2. Реалізувати моделі User, Course, Module, Lesson, Quiz, Question, ProgressRecord (SQLAlchemy + SQLite).
3. Реалізувати реєстрацію/логін через JWT.
4. Написати базові REST-ендпоінти (CRUD для курсів) — тут прямо застосовується навичка "Restful API" з резюме.

### Етап 2. Парсинг файлів
1. Реалізувати модуль вилучення тексту з `.docx`/`.doc` (python-docx), `.pptx` (python-pptx), `.pdf` (pdfplumber/PyMuPDF), `.txt`.
2. Нормалізувати вихідний текст (прибрати сміття, зберегти структуру заголовків).
3. Написати логіку розбиття великого тексту на смислові блоки (за заголовками/довжиною) — основа майбутніх модулів курсу.

### Етап 3. AI-модуль генерації курсу
1. Встановити й налаштувати Ollama локально, завантажити модель (Llama 3.1 8B або Mistral 7B).
2. Спроєктувати промпти для:
   - генерації зв'язного уроку з блоку тексту (з чіткою забороною вигадувати факти поза матеріалом);
   - генерації тестових запитань (одиночний/множинний вибір, коротка відповідь) до блоку.
3. Тут напряму застосовується навичка "Prompt Engineering" / "Generative AI" з резюме.
4. Реалізувати парсинг відповіді LLM у структуровані JSON-об'єкти (уроки, питання, варіанти відповідей).
5. Додати опційний fallback на хмарне AI API (з no-retention політикою) для слабких пристроїв.

### Етап 4. Логіка прогресу й архівації
1. Реалізувати підрахунок % проходження курсу.
2. Реалізувати збереження результатів тестів (QuizAttempt) і розрахунок середньої оцінки.
3. Реалізувати автоматичний перехід курсу в статус "архівний" при 100% + всі тести пройдені.
4. Реалізувати ендпоінти для трьох вкладок акаунту (активні/не розпочаті/архівні).

### Етап 5. Безпека і конфіденційність
1. Додати шифрування вмісту курсів at rest (AES-256, наприклад через `cryptography`).
2. Хешування паролів (bcrypt).
3. Налаштувати HTTPS/тунель (Tailscale або сертифікат Let's Encrypt, якщо хмарний варіант).
4. Перевірити, що жоден лог не містить повного тексту матеріалів.

### Етап 6. Frontend
1. Ініціалізувати React-проєкт з Tailwind CSS.
2. Реалізувати сторінки: логін/реєстрація, завантаження файлів, список курсів (3 вкладки), сторінка уроку, сторінка тесту, прогрес-бар.
3. Забезпечити адаптивну верстку (mobile-first підхід) — під ПК і телефон з єдиної кодової бази.
4. Налаштувати PWA-маніфест для встановлення застосунку на телефон без App Store/Google Play.

### Етап 7. Інтеграція та тестування
1. З'єднати frontend і backend, наскрізне тестування сценарію "завантажив файл → пройшов курс → отримав архів".
2. Написати базові unit-тести для критичної логіки (розрахунок прогресу, парсинг, генерація) — застосування навички JUnit/тестування з резюме (адаптовано під pytest).
3. Ручне тестування на реальному телефоні через Tailscale/локальну мережу.

### Етап 8. Розгортання
1. **Local-first варіант:** розгорнути на власному ПК/домашньому сервері через Docker Compose, налаштувати автозапуск, підключити телефон через Tailscale.
2. **Хмарний варіант (опційно):** backend на Render/Fly.io free tier, frontend на Vercel, БД на Supabase — з обов'язковим шифруванням.

### Етап 9. Ітерація та вдосконалення
